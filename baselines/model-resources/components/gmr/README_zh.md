# GMR：通用人体动作重定向

> 发布状态：此目录目前仅提供说明，未随附 GMR 代码、补丁、机器人资产或人体模型。下面的目录和命令描述此前检查的工作副本，不代表本资源仓库中已包含这些文件。部分行为来自本地修改；对应代码发布前，不应将上游最新版本视为等价替代。

[GMR（General Motion Retargeting）](https://github.com/YanjieZe/GMR) 将人体动作转换为人形机器人的参考动作。本文介绍当前版本的核心功能、安装、资源准备及使用方式，以 Unitree G1 29 自由度机器人为例。

本版本基于上游 GMR，保留原作者署名、许可证和引用。其他机器人及输入类型的原始说明见上游 README；本文命令对应当前工作副本。

## 1. GMR 是什么

GMR 根据人体关节的位置和朝向，通过关节对应关系、身体比例缩放和逆运动学（IK）求解机器人根位姿与关节位置。核心实现使用 mink 和 MuJoCo。

```text
人体动作 → 人体关节位置与朝向 → IK 映射与求解 → 机器人参考动作
                                                  │
                                              保存 / 可视化
```

GMR 重定向本身不需要训练 checkpoint。人体模型参数、机器人描述资源和输入动作是分别准备的依赖。输出是运动学参考轨迹，机器人控制、动力学跟踪和评估由下游系统完成。

## 3. 安装与下载

建议使用独立 Python 3.10 环境，在所使用的 GMR 仓库根目录执行：

```bash
conda create -n gmr python=3.10 -y
conda activate gmr
python -m pip install --upgrade pip
python -m pip install -e .
# 当前 IK 求解器默认使用 daqp。
python -m pip install daqp
```

PyTorch 的 CPU/CUDA 版本按机器选择，见 [PyTorch 官方安装页](https://pytorch.org/get-started/locally/)。常规 GMR IK 可在 CPU 上运行，录像另需合适的图形渲染环境。若遇到 `libstdc++` 动态库错误，可在当前环境安装 `conda-forge::libstdcxx-ng`。

| 资源 | 用途 | 获取方式 |
|---|---|---|
| 固定版本的 GMR 代码 | 核心算法和入口 | 使用维护者发布的版本，上游来源见文首链接 |
| G1 XML/MJCF 和引用网格 | 机器人模型 | 使用该版本配套的 `assets/unitree_g1/`，保留资源许可证 |
| IK 配置 | 人体与机器人的对应关系 | 随代码提供，G1 SMPL-X 路线使用对应的 `smplx_to_g1.json` |
| SMPL-X 人体模型参数 | 从人体参数计算关节 | 从 [SMPL-X 官网](https://smpl-x.is.tue.mpg.de/)注册并接受许可后下载 |
| 符合接口的人体动作 | 重定向输入 | 使用自有或有权使用的动作数据 |

安装 smplx Python 包不会自动下载人体模型。当前加载器使用 `.pkl` 模型文件：

```text
assets/body_models/smplx/
├── SMPLX_NEUTRAL.pkl
├── SMPLX_FEMALE.pkl
└── SMPLX_MALE.pkl
```

只处理 `neutral` 动作时可先准备对应文件。不要通过重命名把 `.npz` 模型当成 `.pkl` 使用。人体模型文件与动作 `.npz` 是不同资源。不需要为了转换一段自有动作下载完整动作数据集，也不需要额外的 GMR 训练权重。

## 4. 使用示例

以下命令在 GMR 根目录执行。`data/human_motion.npz` 是用户准备的输入路径，不代表仓库已附带该文件。

### 人体动作 → G1

```bash
mkdir -p output
python scripts/smplx_to_robot.py \
  --smplx_file data/human_motion.npz \
  --robot unitree_g1 \
  --save_path output/g1_motion.pkl \
  --headless
```

`--headless` 不创建窗口，不能与当前重定向入口的 `--record_video` 同用。批量保存不要加 `--loop`，循环模式不会自然到达最后的保存步骤。

### 播放机器人动作

在具备桌面显示环境的机器上执行：

```bash
python scripts/vis_robot_motion.py \
  --robot unitree_g1 \
  --robot_motion_path output/g1_motion.pkl
```

当前播放器循环播放，可通过终端中断结束。此入口不等于无窗口视频渲染。

### 可选：检查人体骨架

```bash
# 有桌面显示环境：播放人体骨架
python scripts/vis_smplx_motion.py --smplx_file data/human_motion.npz

# 具备 EGL 支持的无桌面环境：输出人体骨架视频
MUJOCO_GL=egl python scripts/vis_smplx_motion.py \
  --smplx_file data/human_motion.npz \
  --record_video --video_path output/human.mp4 --max_frames 120
```

人体工具显示 22 个身体关节组成的骨架，不是完整人体网格；它按 Y-up → Z-up 转换坐标，并根据整段最低关节位置做统一高度平移。

## 5. 输入与输出

### 人体动作 `.npz`

| 字段 | 约定 |
|---|---|
| `root_orient` | `[T, 3]` 根朝向轴角，弧度 |
| `pose_body` | `[T, 63]` 身体局部轴角，弧度 |
| `trans` | `[T, 3]` 人体平移，米 |
| `betas` | 一维、与人体模型兼容的体型系数 |
| `gender` | `neutral` / `male` / `female` |
| `mocap_frame_rate` | 输入帧率 |

当前人体加载流程将手部、下颌和眼部姿态置零，主要处理身体动作。用户应在输入前确认参数形状、单位和坐标约定。

### 机器人动作 `.pkl`

| 字段 | 内容 |
|---|---|
| `fps` | 输出帧率 |
| `root_pos` | `[T, 3]` 根位置 |
| `root_rot` | `[T, 4]` 根四元数，保存顺序为 **xyzw** |
| `dof_pos` | G1 为 `[T, 29]`，顺序由实际机器人模型决定 |
| `local_body_pos` / `link_body_list` | 当前保存入口为 `None` |

MuJoCo 内部根四元数为 **wxyz**，文件保存时转换为 **xyzw**。这只是分量顺序变化，不会损失旋转信息；读取端需要采用对应顺序。

GMR 保存机器人根位姿、关节位置和帧率。各身体部位的世界位姿及速度不在当前保存格式中，需要结合相同版本的机器人模型，通过后处理计算。用于评测时，应固定关节顺序、坐标约定、重采样及速度计算方法。

## 6. 当前版本的处理逻辑、目的与验证范围

本节说明当前代码执行了哪些处理、它们解决什么问题，以及适用条件。下面关于坐标和高度处理的目的，是依据实现解释其作用，不代表已验证它们适用于所有输入，也不应理解为 GMR 的通用要求。

### 6.1 无窗口运行与首帧处理

`smplx_to_robot.py --headless` 用于没有桌面显示环境的服务器及批处理任务：运行 IK 并保存结果，不创建 MuJoCo 窗口。它改变的是显示方式，不会自动转换坐标或补充接触约束。

非循环模式从第 0 帧开始，是为了避免循环索引先自增导致第一帧被跳过；这保证重定向从输入处理后的首帧开始，并不表示重采样前后的帧数一定相同。

### 6.2 显式指定人体模型文件格式

`utils/smpl.py` 在创建人体模型时指定 `ext="pkl"`，与本文要求准备的 `.pkl` 模型文件一致，避免依赖 smplx 包的默认扩展名，也不需要用户修改安装目录里的库代码。这只是加载格式选择，不改变动作数值；若使用 `.npz` 模型，应调整加载接口，不能直接改文件后缀。

### 6.3 根位姿的坐标转换：统一竖直方向

如果一段动作以 Y 轴为竖直方向，而目标世界以 Z 轴为竖直方向，需要对位置与朝向施加一致的旋转。当前保存入口使用 `(x, y, z) → (x, -z, y)` 变换根位置，并对根朝向施加相同旋转，使整段机器人动作一起转向；关节局部角度保持不变。

**适用前提是：待转换的机器人轨迹确实仍采用 Y-up 约定。** 输入文件属于 SMPL-X 格式，并不足以证明这个前提成立。不同数据来源可能已经调整过坐标，而且保存前处理的是 IK 输出的机器人姿态，必须检查它实际采用的方向。

当前实现无条件执行这一步，没有按输入坐标约定自动判断或提供开关。如果轨迹已经正确处于 Z-up 世界，再转换会改变原本正确的朝向。因此，这项处理应在发布前按实际输入验证，并改为由明确的坐标约定控制，不能作为所有动作的默认正确步骤。

这与 `wxyz → xyzw` 不同：前者旋转轨迹，后者仅改变四元数的存储顺序。

### 6.4 整段高度对齐：调整动作相对地面的整体偏移

人体到机器人的比例映射和位姿拟合可能使输出的足部整体偏高或偏低。当前 G1 后处理通过正向运动学，计算整段动作中左右踝部及脚趾 body 原点的最低 Z 值，再对所有帧的根高度加同一个常数：

```text
高度偏移 = 0.005 m − 整段选定足部原点的最低高度
每一帧根高度 = 原根高度 + 高度偏移
```

这一步把选定参考点的最低高度统一到 5 mm。采用整段一致的偏移，是为了保留原有上下起伏和帧间位移，避免每帧都强制贴地而压平跳跃等动作。它同时改变了动作的绝对高度，因此不能不加区分地用于有台阶、平台或明确世界高度要求的数据。

`0.005 m` 是当前实现的默认间隙值，不是已经标定的物理接触高度。body 原点也不一定是脚底碰撞几何的最低点，所以该方法不保证脚底不穿地；个别异常低点还可能使其他帧整体悬空。它不判断支撑脚，不解决脚滑、接触力或动力学可执行性。更完整的接触处理属于后续跟踪或约束求解任务。

### 6.5 为什么要重新加载保存结果检查

当前执行顺序为：

```text
IK 输出 → 在线预览（如启用）
       → 收集整段动作 → 坐标旋转 → 高度对齐 → 保存
```

在线预览展示的是后处理前的姿态，保存文件包含后处理后的姿态。因此，预览正常不能证明保存文件的朝向和高度正确。检查时应重新加载保存文件，并使用相同版本的机器人模型确认结果。

这种差异来自当前实现顺序，并非重定向算法的必然要求。后续可统一为“完成必要后处理后，用同一份数据预览和保存”；由于整段高度对齐需要知道整段最低点，这种预览应在整段重定向完成后进行。
